05 · DATA LIFECYCLE · RECOVERABLE DELETION

Building a Trash experience on object storage that doesn’t have one.

How I defined a recoverable deletion model on top of AWS object storage without physically moving large files into a separate Trash location.

RoleTechnical Product Manager
StageProduct definition
EnvironmentEnterprise data platform
FocusLifecycle · dependencies · recovery

01 · The problem

S3 did not give us a traditional Trash folder.

Our storage layer was built on AWS object storage, where moving large files into a separate Trash location would create unnecessary data movement and cost. We needed to give users the familiar behavior of Trash while leaving the underlying objects in place until they were permanently deleted.

PRODUCT QUESTIONHow do we create a familiar Trash experience without physically moving large objects around S3?

02 · My role & impact

I translated a broad deletion request into explicit lifecycle behavior.

I defined the product requirements and lifecycle behavior with engineering, including how objects enter Trash, how long they remain recoverable, how recovery works, what happens to linked data, and when permanent deletion occurs.

03 · The solution

Create the behavior of Trash without moving the object.

Instead of copying data into a separate Trash bucket, the platform could keep the object in place, mark it for deletion, hide it from the normal experience, and retain it for recovery before permanent purge.

04 · Key product decisions

The judgment calls behind the Trash model.

The familiar UI pattern was simple. The harder decisions were how to reproduce that behavior on object storage without introducing unnecessary data movement, cost or confusing lifecycle semantics.

DECISION 01Keep deleted objects in place instead of moving them to a Trash bucket.+

A literal Trash implementation would mean moving large objects from their existing S3 location into a separate Trash bucket, then potentially moving them again if the user restored them.

THE TRADEOFF

A separate Trash bucket would closely mirror the mental model users already understood, but physically moving large objects would add unnecessary data movement, cost and operational complexity.

THE DECISION

Leave the object in its existing storage location and mark it for deletion instead. The product could then hide it from the normal experience, surface it in Trash and permanently purge it later without copying the underlying data between buckets.

DECISION 02Make deletion recoverable before it becomes permanent.+

Users expected Trash to protect them from accidental deletion, but keeping deleted data forever would continue consuming storage and make the lifecycle unclear.

THE TRADEOFF

Immediate permanent deletion would minimize retained storage but remove the safety users expect from Trash. Indefinite retention would maximize recoverability but leave deleted data and storage costs around with no clear endpoint.

THE DECISION

Introduce a defined retention period between deletion and permanent purge. During that window, users could recover the object by removing its deletion state. After the retention period, the platform could permanently delete it.

What deletion taught me about lifecycle product design.
