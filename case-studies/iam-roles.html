01 · The problem

The safer architecture still had to be adoptable.

Customer-owned S3 storage relied on IAM users and long-lived credentials. Moving to role-based access changed not only the security primitive, but also customer configuration, trust relationships and existing workflows.

PRODUCT QUESTIONHow do we improve security without creating a migration customers cannot realistically adopt?

SECURITY DEEP DIVE

The hard part was choosing where to place trust.

Moving away from long-lived access keys improved the credential model, but the role architecture still determined customer isolation, blast radius, auditability and operational complexity. We evaluated the security tradeoffs before treating any one design as the answer.

01 · SHARED ROLE

Simpler operations, larger blast radius.

+

A single Illumina-managed role minimized setup and avoided creating AWS resources per customer. But sharing one role across customers concentrated risk: a compromise could affect multiple customers, customer-specific auditing was weaker, and customers could not independently revoke access.

+ simpler setup ↔ − isolation & revocation
02 · EXTERNAL ID

Better trust boundaries, but not complete isolation.

+

Unique External IDs added confused-deputy protection and improved traceability when assuming a role. They did not eliminate the shared-role blast radius, and putting many customer IDs into one trust policy introduced policy-size and lifecycle-management limits as the customer base grew.

+ stronger verification ↔ − shared-role scaling
03 · DEDICATED ROLES SELECTED APPROACH

Stronger isolation, more operational overhead.

+

Separating customers or customer tiers across roles reduced the number of customers affected by a compromised role and created clearer audit boundaries. The tradeoff was more provisioning, policy management and infrastructure to operate.

+ smaller blast radius ↔ − management complexity
04 · VPC ACCESS RESTRICTIONS

Tighter network controls could break workflows.

+

Restricting access to trusted network paths strengthened the security posture, but it changed the product experience. Browser and instrument uploads would no longer work in the same way, cross-account copy became more constrained, and applications needed to handle shorter temporary-credential sessions.

+ network restriction ↔ − workflow compatibility
THE PRODUCT TRADEOFFMaximize isolation and auditability without creating a security model customers cannot configure or workflows cannot use.

04 · Key product decisions

The tradeoffs that shaped the work.

DECISION 01Use roles as the target access model.+

Long-lived customer credentials created a security model we wanted to move away from.

THE DECISION

Move toward cross-account role assumption with customer-controlled permissions.

DECISION 02Make trust explicit.+

Cross-account access only works when both sides of the trust relationship are deliberately configured.

THE DECISION

Define the customer and platform responsibilities around role trust and S3 permissions.

DECISION 03Design backward compatibility with the architecture.+

Existing storage configurations could not simply disappear when the target model changed.

THE DECISION

Treat migration behavior as part of the product design rather than an implementation detail.
