03 · AWS cloud platform

Product management below the application layer.

A platform case study in secure customer storage, cloud economics, data lifecycle and multi-tenant compute.

RoleTechnical Product Manager
ScopePlatform strategy and requirements
EnvironmentAWS-based enterprise platform
WorkstreamsSecurity, storage, billing and compute

Problem statement

Infrastructure behavior becomes product behavior at enterprise scale.

The platform had to make cloud primitives usable and governable for enterprise customers. That meant turning questions about AWS identity, storage movement, deletion and shared compute into explicit product behavior, requirements and migration paths.

Solution

Define the product contracts around the infrastructure.

I helped shape multiple platform workstreams by translating architecture and customer needs into requirements: how customer-owned storage should be accessed, what data movement should be metered, what “delete” should mean when resources have dependencies, and how shared compute should behave when workloads compete.

AWSIAM & RBACCross-account accessUsage meteringData lifecycleEvent-driven systemsMulti-tenancyPlatform commercialization

Workstream 01 · Security

Replacing long-lived access keys without breaking customer storage.

Customer-owned S3 storage relied on IAM users and credentials. I helped define requirements and migration strategy for moving toward cross-account role-based access, including trust relationships, customer bucket policies, role assumption, backward compatibility and VPC-restricted workflows.

Core tradeoffImprove the security model while preserving a realistic migration path for customers with existing storage configurations.

Workstream 02 · Cloud economics

Infrastructure cost needed product semantics before it could become pricing.

I helped shape requirements for egress metering and billing, including what movement should count, how usage should be attributed when data was shared, and how storage activity could generate usage records for downstream aggregation. The customer model also needed to translate cloud-provider tiering into understandable platform behavior.

Product lessonCommercialization starts inside the architecture when the system must observe, attribute and meter the behavior you intend to price.

Workstream 03 · Data lifecycle

Delete was a state transition, not just an API call.

I explored a recoverable deletion model across analyses, projects and shared resources. The design needed to account for dependencies, ordering, asynchronous operations, retention, recovery and the point at which deletion becomes irreversible.

Delete request→Hide→Retain→Recover or purge

Workstream 04 · Multi-tenant compute

Fair does not always mean first come, first served.

I contributed to product work for shared batch processing where tenants and workloads competed for compute. The work exposed me to fair queueing, quality-of-service priorities, round-robin scheduling and token-based resource allocation, including the product decisions required when some workloads need higher priority without allowing one tenant to monopolize the system.

I contributed to this work rather than leading it through delivery. I include it because it materially deepened how I reason about multi-tenant platform behavior.

Skills & takeaways

What platform work changed in how I think.

Architecture as product

Identity, lifecycle and metering decisions shape the customer experience even when users never see the underlying services.

Migration matters

A safer or cleaner future state only works if existing customers have a practical path to it.

Commercial thinking

Pricing requirements can change what telemetry and attribution the architecture needs to produce.

Technical fluency

I learned to engage with engineers on cloud and distributed-system concepts while keeping the conversation anchored to product behavior.
