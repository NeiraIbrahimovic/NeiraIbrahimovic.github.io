01 · SIMS · 0→1 enterprise data platform

Building a global identity layer for samples.

A technical product case study in enterprise data modeling, APIs, legacy-system compatibility and cross-functional execution across a genomics software ecosystem.

RoleTechnical Product Manager / Product Lead
Ownership0→1, concept through internal beta
Scale12+ integrating product teams
UsersLab scientists, bioinformaticians and downstream applications

Problem statement

One biological sample could become multiple software identities.

Illumina products had evolved different ways to create and represent samples. A sample planned for sequencing could become disconnected from the files, analyses and downstream interpretation associated with it. Teams and customers could end up reconciling information manually because there was no shared sample identity across the workflow.

The problem was therefore not simply to build a new sample-management UI. It was to create an enterprise layer that could preserve identity, lineage and relationships as data moved across products.

The product direction

A shared sample model with a persistent identity.

I helped define SIMS as the system that could provide a consistent sample identity and metadata model across the ecosystem. The product needed to support run-specific sample instances, aggregation across sequencing runs, links to files and analyses, and integrations that could serve both human workflows and downstream applications.

My role & impact

Product ownership from ambiguity to an executable platform strategy.

My scope included product vision and roadmap, enterprise data-model decisions, API and integration requirements, UX and prototypes, customer discovery, alpha and beta readiness, launch planning and coordination across more than a dozen integrating teams.

I moved between senior-leadership alignment and detailed technical work with engineering and architecture. A large part of the role was translating the same problem at different levels: strategic value for leadership, contracts and behavior for integrating teams, and an understandable workflow for users.

Key product decision 01 · Identity model

The cleanest new model would have broken the old world.

BaseSpace already distinguished run-level Samples from Biosamples that could aggregate across runs. Rather than require an ecosystem-wide rewrite, we established a compatibility model in which a SIMS Run Sample represented the run-specific instance and a SIMS Sample represented the persistent identity that could span runs.

Decision principleDesign the target architecture and the adoption path together. A platform is not successful if its model is elegant but existing products cannot realistically migrate to it.

Key product decision 02 · Release strategy

A platform ships on everybody else's calendar.

SIMS depended on products with different release cadences, security requirements and integration mechanics. During an early release cycle, a downstream code freeze, web-component versioning and security-readiness work created risk close to the planned external milestone.

I prioritized an internal beta before external exposure. The experience changed how I planned platform work: code freezes, security scans, version dependencies and downstream release mechanics became explicit roadmap dependencies rather than implementation details discovered near launch.

Key product decision 03 · Adoption & migration

The hardest work lived between team boundaries.

The new model also required a strategy for existing sample data and API behavior, but the migration crossed several systems and did not have one natural owner. When international teams met in San Diego, I created the working agenda and brought a proposed migration approach into the room. Engineers challenged and refined it until the group had a concrete direction.

That became an important operating pattern for me: when ownership is distributed, make the problem and proposed path tangible enough that the right people can make decisions together.

Skills & takeaways

What SIMS taught me about technical platform product management.

Senior leadership communication

Frame architectural work around customer impact, strategic value, risk and the decision needed without stripping away the technical substance.

Cross-functional execution

A platform roadmap has to model other teams' release mechanics, security work and migration dependencies, not just the owning team's backlog.

Technical product judgment

Data models and API semantics are product decisions when they determine what users and downstream systems can do.

Influence without authority

Integration teams had their own roadmaps. Adoption depended on a clear contract, credible migration path and repeated alignment.
